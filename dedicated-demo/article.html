언리얼 데디케이티드 서버와 클라이언트 반영

언리얼 데디케이티드 서버가 전투 결과를 확정하고 클라이언트가 입력·예측·화면 반영을 담당하는 과정을 보여 준다. 미니버스의 데디케이티드 서버 연동·RPC 동기화 경력을 이해하기 위한 별도 기술 모형이며, 프로젝트의 실제 구현 범위를 추가로 주장하지 않는다. 실제 UE 실행이나 네트워크 연결은 아니며 예시 수치로 4배 느리게 표시한다.

01서버 권한과 화면 분리

서버: 판정·복제 / 클라이언트: 입력·예측·렌더링 · ▶ 이 장면 보기

데디케이티드 서버는 로컬 플레이어가 없는 독립 서버 프로세스다. 게임 규칙·충돌·권한 판정·복제를 처리하며 게임 화면을 렌더링하지 않는다. 중앙의 와이어프레임 화면은 서버 상태의 진단용 개념 뷰로, 서버가 실제 그리는 화면이 아니다.

클라이언트는 입력과 카메라·애니메이션·사운드·HUD를 처리한다. 이 예시는 서버 권한 모델이다. 모든 멀티플레이 게임이 락스텝을 사용하지 않으며, 이 영상에서는 서버가 확정한 상태를 복제한다.

02이동 예측과 서버 보정

저장 이동 전달 → 서버 확인 → 보정 후 재실행 · ▶ 이 장면 보기

표준 CharacterMovement 흐름에서 소유 클라이언트의 Autonomous Proxy는 이동을 즉시 예측하고 이동 데이터를 서버에 보낸다. 서버는 이동을 검증·계산하며 필요하면 보정한다. 클라이언트는 서버 시점으로 보정한 뒤 아직 확인되지 않은 저장 이동을 다시 실행한다. Simulated Proxy의 원격 캐릭터는 수신된 이동 상태를 스무딩한다.

모형에서는 클라이언트 속도에 의도적으로 20% 오차를 주입했다. 서버는 명령당 0.1초 이동을 계산하고 클라이언트는 1.2배로 예측한다. 편도 지연은 0.25초 예시다. ACK 위치를 적용한 뒤 미확인 명령을 재실행해 입력이 끝나면 서버 위치로 수렴한다. 실제 UE의 SavedMove 직렬화·서버 이동 타임스탬프·보정 임계치·패킷 손실 처리는 단순화했다.

03Server RPC와 판정

소유 Pawn으로 요청하고 서버에서 공격 조건 검증 · ▶ 이 장면 보기

클라이언트는 자신이 소유한 Pawn을 통해 Server RPC로 발사를 요청한다. 예시는 조준 방향 같은 의도를 전송하며 피해 값을 클라이언트가 확정하지 않는다. UE는 클라이언트가 서버 RPC를 호출할 때 Actor의 소유 연결 규칙을 적용한다. 서버의 게임 로직은 쿨다운·탄약·거리·적중 등 허용 조건을 검증해야 한다.

모형은 고정된 정지 표적이 조준선 위에 있다고 가정하며 소유자·0.5초 공격 간격·탄약 3발·거리 5 이내를 검사한다. 유효 요청당 피해 30을 서버에서만 적용한다. 6초·7.4초·10.4초의 세 요청이 승인되고 7.5초 요청은 공격 간격 때문에 거부된다. UFUNCTION(Server, Reliable)은 예시 선언이며 모든 공격이나 매 프레임 입력을 Reliable RPC로 보내라는 권장은 아니다.

04HP 복제와 화면 반영

지속 상태는 RepNotify / 일회성 연출은 Multicast · ▶ 이 장면 보기

서버에서 Health를 변경하고 복제 프로퍼티가 수신 클라이언트에 반영되면 OnRep_Health에서 HUD를 갱신한다. C++ RepNotify는 서버의 일반 대입만으로 서버에서도 자동 실행되는 콜백이 아니다. UPROPERTY뿐 아니라 복제 등록·Actor 복제 활성화와 적절한 조건 설정이 필요하다.

피격 FX는 일회성 Unreliable NetMulticast 연출의 예시로 분리했다. 서버에서 호출하며 해당 Actor가 관련된 연결을 대상으로 한다. 첫 공격의 B 연출 패킷은 의도적으로 유실해도 HP 프로퍼티는 도착한다. 지속 상태를 일회성 RPC에만 맡기지 않는 이유다. 모형은 HP를 A에는 0.4초, B에는 0.6초 후 전달하며 이는 실제 UE의 프로퍼티 패킷 신뢰성 구현이 아니다.

B는 모형 시간 9.5–12.5초 동안 연결을 끊는다. 그동안 서버는 세 번째 공격을 처리해 HP를 10으로 만든다. 프로퍼티 복제는 모든 중간 변경에 대한 이벤트 로그가 아니며, 같은 프레임에 바뀐 모든 값과 서로 다른 Actor·프로퍼티·RPC 사이의 일반적인 전역 순서를 보장하지 않는다.

05재접속과 복제 대상

현재 상태 복원 · 연결별 Net Relevancy · ▶ 이 장면 보기

B가 재접속하면 초기 복제로 현재 HP 10을 받는다. 과거의 피격 Multicast를 재생할 필요가 없다. 뒤늦게 참가하는 클라이언트에도 현재 상태를 줄 수 있도록 지속 상태와 연출 이벤트를 나눈다.

프랍의 GOLD 상태는 서버에 이미 존재한다. 처음에는 B의 관련성 범위 밖이라 모형에서 프랍을 보내지 않고, 14.5초에 관련성이 생기면 현재 상태를 전송한다. 이는 연결별 복제 대상 선택을 설명하기 위한 명시적 관심 범위 모형이며 UE의 실제 거리 검사·Actor Channel·Dormancy·Replication Graph/Iris를 구현한 것은 아니다. NetUpdateFrequency는 갱신 고려 빈도이며 모든 클라이언트에 동일한 속도로 확정 전송하는 보장이 아니다.

06소유권과 클래스 책임

GameMode · GameState · PlayerController · ▶ 이 장면 보기

GameMode는 서버에만 존재하며 규칙을 처리한다. GameState는 클라이언트에도 복제할 공용 게임 상태를 담는다. PlayerController는 서버와 해당 소유 클라이언트에 존재하며 다른 클라이언트의 PlayerController는 일반적으로 복제되지 않는다. 타인에게 공개할 플레이어 정보는 보통 PlayerState에 두고 필요한 복제 조건을 정한다.

16.4초에 B가 A 소유 Pawn으로 Server RPC를 요청하면 소유권 불일치로 거부된다. UE에서 이러한 비소유 Actor의 클라이언트→서버 RPC는 네트워크 계층에서 실행되지 않는 규칙을 모형의 서버 분기로 표현했다. 소유권 자체가 모든 치트 방어를 대신하지 않으므로 서버의 게임 조건 검증도 필요하다.

이 영상에 나온 용어는 용어집에 정리했다.
